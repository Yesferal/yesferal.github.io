Content-driven UI on iOS: JSON to SwiftUI

Yesferal Cueva · Sep 1, 2026 · 5 min read

SwiftUI Kotlin Multiplatform Architecture

In a multi-platform mobile product — iOS and Android, sometimes more than one brand — Clean Architecture and native UI still leave a practical problem: how do you change home-screen composition without rewriting SwiftUI and Android views every time, and without letting the two platforms drift apart?

That is what content-driven UI is for. Structure comes from data; presentation stays native. A configuration describes what appears and in what order; each platform renders it with its own toolkit. This post teaches the design with a concrete use case. That problem is what led me to ship a shared content/contract layer (including Kotlin Multiplatform) while building production event apps.

A concrete scenario

Think of a home screen as an ordered list of section types, for example:

  • a hero or featured carousel
  • a “upcoming” list with a title
  • a promotional card
  • a call-to-action block

Brand A might show carousel → list → CTA. Brand B might show list → promo → carousel. Same section types, different composition. Same native components underneath.

Without a content-driven approach, that difference often becomes duplicated view code — or flavor forks and #if brand branches that are hard to keep honest across platforms.

What you are trying to protect

Three goals show up again and again in this scenario:

1. One contract for two platforms. Android and iOS should agree on what a “screen document” is: which section types exist, what payload each one carries, which navigation targets are allowed. If Android already models the home screen as data, iOS should not invent a second schema.

2. White-label without rewriting UI. New brand ≈ new configuration, not a new app fork. Shared components stay shared; only composition changes.

3. Structure changes without redeploying look-and-feel. Moving a section or swapping order should be a data/config change when possible. Fonts, colors, motion, and accessibility stay in SwiftUI (and the Android UI layer).

If your team is living through “small layout tickets that touch every client,” you are already in this use case.

How to split the system

A clear way to draw the boundaries:

┌───────────────────────────────────────────┐
│  Content configuration (per brand)        │
│  Which sections exist, and in what order  │
├───────────────────────────────────────────┤
│  Shared layer (e.g. Kotlin Multiplatform) │
│  Screen definition, navigation targets    │
├───────────────────────────────────────────┤
│  Native presentation (SwiftUI / Compose)  │
│  Look, feel, platform behavior            │
├───────────────────────────────────────────┤
│  Navigation (Router)                      │
│  Tab switches, pushed screens, links      │
└───────────────────────────────────────────┘

Read it top to bottom as a lesson: who owns structure, who owns meaning, who owns pixels, who owns movement between screens. Each layer should have one job. The design is about what can cross a boundary — and what should not.

Structure vs presentation

Teach this distinction early:

  • Structure = “there is a carousel, then a titled list.”
  • Presentation = “how that carousel looks and animates on iOS.”

The content layer defines section types and order. It does not define fonts, spacing, or brand chrome. Different brands reuse the same types with different composition.

On the UI side, map each section type to a native component. Views should render a typed model — they should not open a raw JSON file and decide layout policy themselves. That keeps presentation testable and keeps configuration boring (in a good way).

Why a shared layer helps

A shared module (Kotlin Multiplatform is one option) can own:

  • section type definitions
  • navigation targets
  • the shape of the “render document”

Both apps then ask the same question from the same place: what should this screen contain? Parsing and validation live here so you do not maintain two incompatible models. This layer is not UI — that is the whole point.

SwiftUI’s job on iOS

SwiftUI (or UIKit, if that is your stack) owns the experience: layout polish, accessibility, gestures, platform conventions. Translate the shared contract into a small set of presentation models the view layer understands.

Rule of thumb: if it is visual behavior, it is native. If it is composition of the screen, it is data.

Navigation as its own concern

Configuration can say “open Upcoming” or “open this URL.” That is a destination, not a navigation implementation. A router turns destinations into actions: switch tab, push detail, open in-app browser.

Views report intent; they do not own the full navigation graph. As the home screen grows, that separation is what keeps the flow readable — the same idea many Android codebases already use with centralized navigation.

Checklist you can take to your team

  • Structure is data. Screen composition lives in configuration, not scattered in views.
  • Presentation is native. Each platform keeps its own look and feel.
  • The contract is shared. iOS and Android read one screen definition.
  • Navigation is centralized. Views pass targets; one layer executes them.

What you gain (and what you trade)

You pay a bit of upfront structure: contracts, mappers, a router. You gain a screen model that scales across platforms and brands without forking UI for every experiment.

If that sounds like a problem your team already has — multi-platform home screens, white-label variants, layout tickets that never stay in sync — this design is meant to be reusable. You can adopt the boundaries even if your stack differs (Compose on Android, a different shared module, or config that later comes from a server).
