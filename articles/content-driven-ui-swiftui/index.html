Content-driven UI on iOS: JSON to SwiftUI

Yesferal Cueva · Sep 1, 2026 · 5 min read

SwiftUI Kotlin Multiplatform Architecture

HornsApp and Muvin are event apps on Android and iOS. We have two brands and two platforms, and the home screen changes often. If we hardcode the layout in SwiftUI, we duplicate structure in every variant and we risk falling out of sync with Android.

The main idea is simple: structure comes from data, and presentation stays native. A content configuration file describes what appears on screen and in what order. Each platform renders it with its own UI tools. This post is an overview. Later articles will go deeper into each part.

The problem we were avoiding

Before this approach, changing the home screen was slow and easy to get wrong. Reordering a section meant editing SwiftUI in several places. HornsApp and Muvin could drift apart, and iOS could fall out of sync with Android without us noticing right away.

We wanted layout changes to be a configuration update — not a hunt through view code on every platform and every brand.

What drove the design

Three constraints shaped how we built this.

Same contract on both platforms. Android already uses a content-driven model. On iOS we follow the same render contract instead of creating a second schema. One definition of the home screen, two native apps.

White-label without rewriting the UI. HornsApp and Muvin share the same codebase but not the same home screen. Each brand has its own content configuration: different sections, different order, same UI components underneath. A new brand means a new config file, not a new fork of the app.

Faster layout changes. We should be able to move a carousel, add a section, or reorder blocks without redeploying presentation code. That is a configuration change. Colors, fonts, and animations stay in SwiftUI.

How the layers work

┌─────────────────────────────────────────┐
│  Content configuration (per brand)      │
│  Which sections exist, and in what order  │
├─────────────────────────────────────────┤
│  Shared layer (Kotlin Multiplatform)    │
│  Screen definition, navigation targets    │
├─────────────────────────────────────────┤
│  Native presentation (SwiftUI)          │
│  Look, feel, platform behavior          │
├─────────────────────────────────────────┤
│  Navigation (Router)                    │
│  Tab switches, pushed screens, links    │
└─────────────────────────────────────────┘

Each layer has one job. The design is about what can cross a boundary — and what should not.

Structure vs presentation

The content layer defines what is on screen: a carousel, a titled list, a call-to-action block. It does not define fonts, colors, or spacing. That belongs to presentation.

HornsApp and Muvin each have their own configuration. They use the same section types but with different composition. The presentation layer maps each section type to a native component. Views do not parse raw JSON.

That separation is intentional. Views render. They do not read configuration files.

Shared layer between iOS and Android

A Kotlin Multiplatform library owns the screen definition: section types, navigation targets, and the shape of the render document. Android has used this for years. On iOS we use the same contract instead of maintaining a second source of truth.

This layer is not UI. It is what both platforms use to answer the same question: what should this screen contain? Parsing, validation, and domain models live here.

SwiftUI as the presentation layer

SwiftUI handles everything the user sees and interacts with. On iOS, we translate the shared contract into a typed presentation model — a set of section types that the view layer understands.

The look and feel stay fully native. Animations, accessibility, and platform conventions do not belong in a configuration file. Structure comes from data. The user experience comes from SwiftUI.

Navigation in one place

The configuration can say where to go: open Upcoming, open a URL. But describing a destination is not the same as navigating to it. A dedicated navigation layer turns that into action — switch a tab, push a detail screen, or open an in-app browser.

Views do not navigate on their own. They pass the target to the router, and the router decides. Tab switches and pushed screens live in one place, similar to Android. This keeps navigation easier to follow as the home screen grows.

Principles we follow

  • Structure is data. Screen composition lives in configuration, not in view code.
  • Presentation is native. Each platform renders with its own tools and conventions.
  • The contract is shared. iOS and Android read the same screen definition.
  • Navigation is centralized. Views pass targets; one layer handles the rest.

What we gain

We invest a bit more structure upfront, but we gain flexibility over time: two brands, two platforms, one way to describe a home screen. Mappers, routers, and platform adapters are implementation details. They can change without rewriting the overall design.
