Content-driven UI on iOS: JSON to SwiftUI

Yesferal Cueva · Sep 1, 2026 · 5 min read

SwiftUI Kotlin Multiplatform Architecture

HornsApp and Muvin are event apps I maintain on Android and iOS. On iOS, the home screen layout comes from a JSON file: it lists the sections and their order, instead of hardcoding everything in SwiftUI.

Android already works this way. This post explains how the same content-driven approach fits on iOS. It is an overview — later articles will cover each part in more detail.

Why do this?

Three reasons drove the design.

One JSON contract, two native apps. HornsApp already has an Android client. iOS and Android read the same render format. Change the home layout once and both apps speak the same language — SwiftUI on one side, Jetpack Compose on the other.

White-label without rewriting UI. HornsApp and Muvin are two products built from the same codebase. Each app ships its own app_render.json: different sections, different order, same SwiftUI views underneath. New brand? New JSON file. Not a new app rewrite.

Ship layout changes faster. Want a carousel up top and an “Upcoming” block below? Edit JSON. SwiftUI still owns pixels, fonts, and animations. The JSON file only decides what goes on screen.

1. JSON describes the layout

A home screen document is a list of blocks. Each block has a key that maps to a UI element:

{
  "views": [
    { "key": "ROW_VIEW", "children": { "key": "CAROUSEL_CARD_VIEW" } },
    { "key": "COLUMN_VIEW", "data": { "title": "Upcoming" } }
  ]
}

HornsApp and Muvin can ship different files with the same keys. A row becomes a carousel. A column becomes a titled list. Swap the file, change the screen — no SwiftUI rewrite.

2. KMP core reads the JSON

Both platforms share a Kotlin Multiplatform library. It loads the render document and exposes typed models — ScreenRender, ViewRender, navigation keys.

Android has used this for years. iOS plugs into the same models instead of inventing a second JSON schema. Parsing stays out of the view layer on both sides.

3. SwiftUI renders the UI elements

On iOS, a mapper turns each ViewRender into something SwiftUI understands:

enum ViewData {
    case carousel(...)
    case title(title: String, route: Route?)
    case seeMore(...)
}

One render(_:) function switches on that enum and draws the right component. Look and feel stay native. Structure comes from JSON.

4. Router handles navigation

JSON can attach a navigation key to a section — “go to Upcoming”, “open this link”. A small Router decides the action:

router.navigate(to: .upcoming)    // switch tab
router.navigate(to: .details(...)) // push screen

Views do not push screens themselves. They hand off to the router. Tab switches and stack pushes live in one place — same pattern Android already uses.

The flow in one line

app_render.json → KMP core → ViewData mapper → SwiftUI → Router

JSON for layout. KMP for shared models. SwiftUI for native UI. Router for navigation. Two app targets, two JSON files, one architecture.
